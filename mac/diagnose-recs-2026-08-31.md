## 結論を先に

**疑っていた「451本の針による部分一致の巻き添え」は、原因ではなかった。**
現在の Firebase の値で index.html の判定をそのまま再現すると、
**部分一致で落ちる rec は 0件**。しきい値を 6/8/10/12 のどれに変えても
表示件数は 1件も動かない（後述の表）。閾値をいじっても何も解決しない。

代わりに見えたのは 3つの別々の問題である。

1. `recommendations` の 60枠のうち **51枠が「すでに却下済みの rec」で埋まっている**。
   アプリは却下した rec を `dismissed` に足すだけで `recommendations` からは消さない。
   一方 build-recs は上限 60件で古い順に切るので、**新しい rec が入る余地が
   毎日削られている**。今日は「既存 60 + 新規 13 − 整理 13 = 60件」だった。
2. build-recs の重複判定・却下済み判定が、**保存するタイトルとは別の文字列**を
   見ている。素材の生タイトルで照合し、保存するのは書き換え後のタイトル。
   そのため一度却下したものが毎日そのまま作り直され、アプリ側で
   `dismissedTitles` の**完全一致**に当たって黙って消える。今日は 13件中 4件。
3. 今日選んだ 13件のうち 1件（r625）は Firebase に届いてすらいない。
   同じバッチ内の別 rec と、正規化後のタイトルが一致して上書きされた。

ただし **「0件」そのものは再現できなかった。** 現在の値では 5件が表示条件を
通る。この食い違いの理由は**わからない**（§7 に書く）。

## 6b. 今日のバッチ 13件がどこで減ったか

`recs-built-preview.json`（13件, r624〜r636）を追跡した。

| 段階 | 件数 | 内訳 |
|---|---:|---|
| build-recs が選定 | 13 | |
| Firebase に到達 | 12 | r625 が欠落 |
| うちユーザーが今日却下 | −3 | r626, r627, r628 |
| うち `dismissedTitles` 完全一致で非表示 | −4 | r624, r632, r635, r636 |
| **表示条件を通る** | **5** | r629, r630, r631, r633, r634 |

### r625 が消えた理由（再現済み）

`scripts/build-recs.mjs` の `prune()` を `recs-backup.json`（バッチ実行直前の
退避）＋ preview で再実行したところ、**実際の Firebase の 60件と ID 順まで
完全に一致した**。r625 は、同じバッチ内の r632 と、`norm()` 適用後の
タイトルが一致したため後勝ちで上書きされた（`byTitle.set` は後から来た方を残す）。
生のタイトルは 47文字と 45文字で別物だが、`build-recs.mjs:76` の `norm()` は
空白・記号（`・`、句読点、引用符、`|` など）を全部除去するので、正規化後の
40文字キーが一致した。

### r624 / r632 / r635 / r636 が非表示になる理由（本命）

この 4件は、`dismissedTitles` の要素と**完全一致**している。
なぜ却下済みのものが再提案されるのか。`scripts/build-recs.mjs` を読むと:

- **476-479行**: 除外判定は `norm(item.title)` と `isDismissed(item.title, …)`、
  つまり **素材（メール・X）の生タイトル**で行う
- **516行**: 実際に保存する rec は `toRec(s.item)` が作る。
  `toRec` は `toTaskTitle(rawTitle, item.desc).slice(0, 60)` で
  **タイトルを「タスクらしい文言」に書き換える**
- アプリが `dismissedTitles` に積むのは、この**書き換え後**のタイトル

**照合する文字列と、保存・却下される文字列が別物になっている。**
生タイトルは日々ぶれるので `isDismissed` をすり抜け、書き換え後は同じ文言に
収束するので `dismissedTitles` に当たる。結果、同じものが毎日作られては
アプリ側で黙って消される。今日のログでは `却下済み 41件` を弾いた上で、
なお 4件がすり抜けている。

正規化も 2種類が混在している。

| 場所 | 正規化 |
|---|---|
| `build-recs.mjs:76` `norm()` | lowercase ＋ 空白・記号を除去 |
| `index.html:307` | `trim()` ＋ `toLowerCase()` のみ |

同じ「同一タイトル」を、2つの違う物差しで測っている。

### 却下済み rec が枠を食い続ける

アプリの `dismissRec`（index.html:525）は `dismissed` と `dismissedTitles` に
追記するだけで、`recommendations` からは削除しない。
build-recs は `MAX_TOTAL=60` で古い順に切る。
そのため **60枠のうち 51枠が「二度と表示されない rec」で占められ、
新規 13件のうち 13件分の古い枠が押し出される**という回転になっている。
今日のログ: `既存 60 + 新規 13 − 整理 13 = 60件`。

### 材料側も細っている

`mac/logs/daily.err.log` に `⚠️ 13件で、目標の 15件に届いていません（材料不足）`。
Gmail は 3アカウント中 2つが `リフレッシュトークンが失効` で、
収集は 6件（同ログ内の前の実行では 34件）。母数が減れば選定も細る。

## 7. 所感（5行以内）

1. 疑っていた部分一致の巻き添えは**実測 0件**で、閾値を何に変えても表示は 5件のまま。原因ではない。
2. 本当の詰まりは 2つ。**60枠の 85%が却下済み rec で埋まっている**ことと、**却下判定が保存するタイトルと違う文字列を見ている**こと。
3. **「0件」は再現できなかった。** 現在の値では 5件（r629/630/631/633/634）が通り、この 5件は構造も正常（title 14〜59文字、desc あり、url あり）で `dismissed` にも入っていない。公開中の index.html は手元と**バイト一致**を確認済み（フィルタ行を diff、差分なし）なので、古い版が配信されている線ではない。
4. 推測: 観測時点と現在で状態がずれた可能性がある。`dismissed` の末尾 3件が今日の ID なので、**今日アプリ上で少なくとも 3件は表示されていた**。その前後で「0件」を見たのかは**わからない**。端末側のキャッシュや読み込み失敗（`extractRecs` が null を返すと `recs` は INIT_RECS の 24件のままになり、その 24件は ID r1〜r24 が全部 `dismissed` 済みなので**表示 0件になる**）も筋は通るが、それなら tasks も読めないはずで、裏は取れていない。
5. 推測: 直すなら閾値ではなく、①却下済み rec を `recommendations` から外して枠を空ける ②`isDismissed` / `seen` を**書き換え後のタイトル**で照合する ③正規化を 1本に統一する、の順に効くと思われる。
